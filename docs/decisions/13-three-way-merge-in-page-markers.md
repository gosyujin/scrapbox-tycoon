# 13. 競合コピーをやめて 3-way マージ + ページ内マーカーにする (同期の安全化 段階2)

## 経緯

2026-10-30 の実データ (notes リポジトリのコミット履歴) で、競合を解消しようとして競合が連鎖していた:
14:27 に端末 A が統合して `(sync conflict)` を削除 → 14:28 に端末 B が (削除済みのコピーが残ったまま)
本体を編集して `(sync conflict)_2` を作る → 14:29 にまた `(sync conflict)` ができる、の繰り返し。
10/17〜18 の `(sync conflict)_2 (sync conflict)` も 12 日間残っていた。

構造上の原因は、競合コピーが**普通のページとして全端末に配られる**こと。各端末がそれぞれ解消しようとし
(本体を編集 + コピーを削除)、その解消編集が相手の編集と食い違って新しい競合になる。

## 設計

- 同じページを両側が変えていたら、**基準版 (最後に同期した版) との 3 者で行単位にマージ**する (`src/merge.ts`)。
  - 別の行の編集 / 末尾への追記同士 (古い方が先) → マーカーなしで両方残る。
  - 同じ行の別々の編集、削除 vs 編集 → ページ内に両方を `<<<<<<< 競合: 先に保存された版` /
    `=======` / `>>>>>>> 競合: 後に保存された版` で挟んで残す。別ページは作らない。
- **基準版は git 履歴から取る。** `meta.baseCommit[title]` = そのページが「最後に同期した内容」だったコミット。
  pull で取り込んだ時は pull したコミット、push した時は push が作ったコミット (`pushBatch()` が sha を返す)。
  ローカルに基準版のコピーを持たない (localStorage を食わない)。無ければ両者が共有する行だけを基準にする
  (`commonLines()`: 違う部分はすべて両側の変更扱い → マーカーになるだけで、何も消えない)。
  古い meta (`baseCommit` なし) は pull の時に `lastSyncedUpdated` が一致するページから順次埋まる。
- **マージは対称・決定的。** `merge3(base, x, y)` = `merge3(base, y, x)`。マーカーの 2 面は「自分/相手」ではなく
  ページの `updated` (同じなら本文) の順で並べ、マーカーに端末名や時刻を入れない。マージ結果の `updated` は
  `max(両方) + 1`。2 台が同じ食い違いをマージしても同一ページになり、後から push する側は
  remote と自分が同一内容で、争うものが残らない。
- **解消は普通の編集。** バナー (`app.ts`) の「先の版を残す / 後の版を残す / 両方残す」は該当ブロックを
  置き換えて `savePage` するだけ。2 台が同じ選択をすれば差分が同じなのでマージはきれいに通る。
  別の選択をしても、同じ範囲に対する 2 つの置換なので新しいマーカーブロックが 1 つできるだけで、
  ページが増えることも、ブロックが入れ子になることもない (テストで確認)。
- `lines[0]` (ページの identity) はマージ対象から外し、マーカーが 1 行目に来ないようにする。
- `pull()` は 1 つのコミット (`runSync()` が直前に読んだ HEAD) のスナップショットから全ページを読む
  (`GitHubStore.snapshotAt()`)。ページ毎に tree を取り直さなくなり、一覧と本文が別時点になることもない。
- 状態表示: `SyncStatus.conflictTitles` = マーカーを含むページ + 旧 `(sync conflict)` コピー。一覧のカードに
  「⚠ 競合」を出し、バッジは橙になる。

## 既存データ

旧版が作った `(sync conflict)` ページは自動では消えない (従来どおり、開いて「このコピーを削除」/
「元ページに統合する」で処理する)。新しい競合コピーは作られない。→ [troubleshooting](../troubleshooting.md)

## 既知の限界

- 行が識別子になるので、同じ内容の行が複数ある箇所の編集は diff が曖昧になり得る (LCS の素朴な実装)。
- 同じ秒に別々の端末が保存すると `updated` が並ぶ。その場合も本文で順序が決まり、結果は決定的。
- `>>>>>>>` の行は記法パーサ上は引用 `>` として描画される (見た目だけ。バナーが主な操作面)。
- rename (旧タイトル削除 + 新規) と別端末での旧タイトル編集の衝突は未対応 (編集側が復活する)。安定 ID 化は未着手。

## 回帰テスト

`test/merge.test.mjs` (マージ関数: 対称性・追記・同一変更・削除対編集・マーカー操作・同じ解消)、
`test/sync-conflict.test.mjs` (2 台: きれいなマージ / マーカー / 同時マージの収束 / 同じ解消 / 別々の解消 /
基準版なし)。
